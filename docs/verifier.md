# Verifier — 3단계 검증

MAI는 사용자에게 공개하지 않은 임시 답변을 검증한 후, **PASS일 때만 임시 답변 그대로 출력**하고 모델 실행을 종료함. REJECTED 시 해당 임시 답변을 사용자에게 출력하지 않으며, 거절 사유와 수정 계약을 본체 모델에 전달하고 **툴을 다시 호출할 수 있는 다음 라운드**로 복귀함. 재조회한 근거를 바탕으로 새 임시 답변을 제출할 수 있음.

## 모델 호출

1. **기존 Numeric Reviewer**: A/B/C 분리 전 버전(`de9c60fe`)의 숫자·날짜 검증 코드 및 판정을 복원함. 숫자·날짜의 결정적 검사에서 미확인 사실이 발견되면 별도 LLM으로 동치 여부를 검증함. **숫자 검증 LLM 호출은 조건부**이며, 언제나 3회를 호출하는 구조는 아님.
2. **Coverage + 주장·근거 준비**: 사용자 요구와 현재 성공 툴 결과를 바탕으로 필수 결과 누락 여부를 판정함. **Coverage 거절**이면 짧은 거절 사유만 반환하며 세 번째 호출은 생략함. 통과하면 객관적인 사실 주장과 해당 원문 출처를 **`{claim, source_index, tool, excerpt}` JSON**으로 묶음. 근거를 못 찾으면 출처를 `null`로 명시함. 원문 인용문은 실제 관측된 툴 출력 또는 사용자 원본 메시지에 존재하는지 Python에서 검증함. 인용문을 조작하거나 출처가 틀리면 승인하지 않고 계약 위반 예외를 발생시킴.
3. **Grounding + Alignment/Action 최종 판정**: 두 번째 단계의 구조화된 JSON, 임시 답변, 사용자 요청 및 대화 맥락을 읽고 각 사실 주장이 출처와 일치하는지, 작업 완료 증거가 있는지, 사용자의 요청을 충족하는지 평가함. 전체 툴 원문은 이 단계에 전달하지 않음. 승인하거나, 주장별 결함과 실행 가능한 짧은 수정 요청을 반환함.

## 거절·승인 경로

```text
본체 모델 → 도구 실행 → 임시 답변
    → Numeric Reviewer (해당될 때)
    → Coverage + 주장·근거 준비
       ├─ Coverage 부족 → REJECTED → 본체 모델의 툴 사용 가능 라운드
       └─ Coverage 충분/불확실 → 근거 JSON
                → Grounding + Alignment/Action
                   ├─ PASS → 임시 답변 그대로 출력
                   └─ REJECTED → 본체 모델의 툴 사용 가능 라운드
```

- 기존 `mai/agent/loop.py`의 임시 답변 거절/피드백 전달 및 재시도 예산 처리를 유지함.
- 모델 재시도가 본체 응답 계약이나 오류를 감추지 않음. 스키마 위반·인용문 허위 생성·툴 실패는 자동 PASS되지 않음.
- 이 설계는 **2단계에 원문 의미 검색을 맡기므로 문자열 일치 검색 단계에 의존하지 않음**. 다만 원문 일부를 발췌하는 단계에서 실제 인용문을 만들어낼 위험을 별도로 검증해야 함.
- 기존 숫자 검증의 근거 선택/호출 조건을 포함한 코드를 복원했으며, 새로운 후속 두 호출의 실제 속도는 Ollama 측정 필요함.
- 기억 저장은 검증기와 별도의 파이프라인이며 여기서 수정하지 않음.

## 구조 기반 근거 색인 및 검증

2단계 모델 호출 직전 Python이 성공한 툴 결과를 `json.loads`로 해석할 수 있으면 **실제 JSON 트리의 말단 값**마다 `e0`, `e1` 등의 참조 ID를 부여함. 원본 도구 이름, 원본 실행 인덱스, JSON 경로(`path`), 해당 값(`value`)을 Python이 함께 저장함. JSON이 아닌 일반 문자열 툴 결과와 사용자 메시지는 **문자열 전체를 한 개의 말단 값**으로 등록함. 실패한 툴 결과는 색인하지 않음.

2단계 LLM은 `{claim, evidence_refs: ["e0", "e5"]}` 형태로 사실 주장별 참조 ID만 선택함. **인용문 직접 작성이나 문자 좌표 계산은 하지 않음.** Python이 모델이 지정한 ID를 사전 조회해 정확한 원문 값과 구조 경로를 3단계 입력 JSON에 삽입함. 존재하지 않는 참조는 `invalid_reference`, 선택한 참조가 없으면 `unlocated`, 실제 참조 ID이면 `valid`로 표시함.

`valid`는 **참조가 존재한다는 판정**이며, 근거 내용이 주장에 의미적으로 부합한다는 판정은 아님. 3단계 LLM이 출처의 범위·시점·의미적 타당성을 판단하며, 무효·미발견 참조만 가진 주장을 승인하면 프로토콜 오류로 드러남.

주의: JSON 문자열 안에 대량의 비구조화 문서가 들어 있으면 그 문자열은 통째로 하나의 말단으로 남음. 이 경우 길이 절감은 제한적이지만, 임의 문장 분할이나 문자열 검색으로 출처를 변형하지 않음. 증거 ID는 각 검증 실행 내에서만 유효하며 영구 ID가 아님.

기억 저장 파이프라인은 변경하지 않음.
