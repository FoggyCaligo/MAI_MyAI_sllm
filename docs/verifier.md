# Verifier 구조

최종 답변 검증기는 **A(요청 충족) → B(주장 추출) → Python(근거 검색·색인) → C(근거 검증)** 순서로 동작함. 실제 구현은 `mai/agent/verification.py`, `mai/agent/loop.py` 참고.

## 처리 흐름

```text
본체 모델의 최종 답변 후보
       │
       ▼
[A] 요청 충족 / Coverage / Action 검증 (LLM)
       ├── REJECTED → 사유를 본체에 반환 (B, C 미호출)
       └── 통과
            ▼
[B] 사실 주장·숫자·날짜 및 검색어 추출 (LLM)
            ▼
[Python] 툴 증거 원문 색인·문자열 위치 검색
            ▼
[C] 검색된 근거의 의미 검증 (LLM)
            ├── PASS
            └── REJECTED → 주장별 사유 반환
```

A가 거절하면 LLM 검증 호출은 기본 1회이며, 통과하면 A/B/C 3회임. 오류 재시도 및 본체의 답변 재작성 호출은 별도임. **A/B/C는 `think=False`로 호출**하며, 본체 모델의 Thinking을 검증 입력으로 사용하지 않음.

## 툴 증거의 범위·출처

- AgentLoop는 **마지막으로 툴을 실행한 모델 라운드**의 툴 실행 결과를 Verifier에 전달함. 이 범위는 대화 메시지가 아닌 모델 라운드 기준임.
- 성공한 툴 결과만 근거로 사용함. 툴 실패를 근거 성공으로 해석하지 않음.
- A에는 선택된 범위의 성공 툴 결과를 **각 결과의 본문 전체**와 툴 이름·결과 인덱스와 함께 전달함. 기존 툴 결과당 **1,800자 발췌 제한은 제거됨**. 이 때문에 긴 파일을 읽은 직후 A의 입력이 커질 수 있음.
- Python의 `_indexed_evidence()`는 성공 툴 결과를 본문 손실 없이 결합하고, 툴별 **이름, 인덱스, 시작·종료 문자 위치**를 보존함.
- 사용자가 제공한 메시지 본문도 `user_input` 출처로 별도 색인함. 사용자 진술은 진술의 존재를 입증하지만 외부 상태의 사실성을 자동 확정하지는 않음.
- C에는 전체 corpus가 아니라 B의 주장 및 검색된 출처별 주변 문맥만 전달함.
- 마지막 툴 실행 라운드 이전의 결과는 검색 범위 밖임. 최종 답변 라운드에 툴 호출이 없는 것은 일반적이므로 마지막 툴 실행 라운드를 기준으로 함. **검색 미발견은 반증이 아님**.

## A — 요청 충족·Coverage·작업 완료 검증

**입력:** 최신 사용자 요청, 최근 대화 맥락, 답변 후보, 해당 범위의 성공한 툴 결과 **전체 본문**.

`_TaskReview`의 구조화된 결과는 아래와 같음.

| 필드 | 값 | 의미 |
|---|---|---|
| `alignment_verdict` | `aligned` / `misaligned` / `uncertain` | 사용자의 필수 요청에 부합하는지 |
| `coverage_verdict` | `sufficient` / `insufficient` / `uncertain` | 이미 관측된 중요 정보가 빠졌는지 |
| `action_verdict` | `not_applicable` / `verified` / `unverified` / `contradicted` | 상태 변경 완료 주장이 실제 결과로 확인되는지 |
| `reasons`, `coverage_reasons` | 문자열 배열 | 구체적 거절 근거 |

`misaligned`, `insufficient`, `unverified`, `contradicted` 판정 중 하나라도 발생하면 B/C 호출 없이 즉시 REJECTED 처리함. 필수 거절 사유가 비어 있는 등 계약 위반은 `OllamaProtocolError`로 표출함. A는 사실 주장별 근거의 진위를 검증하거나 주장을 추출하지 않음. 문체·선택적 부연설명·완전한 목록을 임의 필수 조건으로 만들지 않고, 이미 관측한 필수 결과의 실질적인 누락에만 거절 판정을 사용함.

정직한 부분 완료 및 실패 보고는 그 사실만으로 거절하지 않음. Coverage는 *실제로 관측한* 중요 자료의 누락만 대상으로 하며, 검증되지 않은 주장을 포함하라고 요구하지 않음. 외부 상태 변경은 단순 명령 성공과 작업 목표의 결과 상태를 구분함.

## B — 독립 주장 추출기

**입력:** 최종 답변 후보만. **출력:** `_ClaimExtraction.claims` 배열.

각 요소는 `claim`(답변 내 검증 대상 주장)과 `queries`(툴 원문에서 검색할 문자열 목록)로 구성됨. 숫자·날짜·작업 완료 주장·구체적 사실 관계가 포함됨. B는 요청 충족, Coverage, Action 또는 주장 참·거짓을 판정하지 않음.

## Python — 텍스트 합치기·색인·검색

`_indexed_evidence()`는 성공 툴 결과를 하나의 텍스트로 연결하고 각 출처의 시작/끝 위치를 기록함. `_retrieve_claim_evidence()`는 B의 검색어로 정확한 구절 검색 뒤 대소문자 무시 검색과 검색어 토큰의 근접 검색을 수행함. 검색 결과 자체로 참·거짓을 판단하는 문자열 휴리스틱은 사용하지 않음. C에는 색인된 검색 발췌만 전달하며 전체 툴 결과는 전달하지 않음.

현재 구현은 각 검색 적중 지점의 앞뒤 최대 **500자**(설정: `.env`의 `VERIFIER_EVIDENCE_CONTEXT_CHARS`, 기본 500)를 가져온 뒤, **같은 원본 툴 결과 내에서 겹치는 구간을 병합**하여 한 번씩만 보관함. 제목이 있으면 별도 보관함. C는 중복 없는 `lightweight_evidence`를 먼저 읽고, 주장별 `claim_index`의 `evidence_id`와 원문·발췌 상대 좌표로 내용을 참조함. C에 전체 툴로그는 전달하지 않음.

반환 데이터는 `tool`, `tool_result_index`, `start`, `end`, `context`, `search_status` 등으로 구성됨. 미발견은 `not_located_in_selected_scope`로 표기하며 해당 범위에서 검색 문자열을 찾지 못했다는 뜻일 뿐임.

러시아어 원문과 한국어 답변처럼 언어가 다르거나 의역된 경우 리터럴 검색은 실제 근거를 놓칠 수 있음. 검색 누락을 전체 근거의 부재나 모순이라고 단정해서는 안 됨.

## C — 개별 주장 근거 판정

**입력:** B의 주장 목록, Python이 색인한 근거 발췌·툴 출처, 검색 범위 정보. **사용자 요청·대화 전체는 받지 않음.**

C는 `_FinalReviewPayload`로 `evidence_verdict`, `claims`, `reasons`, `retry_summary`를 반환함. 각 주장은 `supported` / `unsupported` / `uncertain`과 함께 `none`, `scope_expansion`, `contradiction`, `unsupported_inference`, `missing_evidence` 중 결함 유형 및 구체적인 사유를 가짐.

중요 규칙:
- 번역·요약·재작성은 **표현의 문자 일치가 아닌 원문 의미 충실도**로 판단함.
- 숫자·날짜·쉼표 표기, 합리적인 근삿값·뒷자리 생략, 단위 환산이 사실상 동일하면 인정함. 문자 수와 파일 크기 등 측정 대상을 혼동하지 않음.
- 근거의 범위를 넘는 단정, 증거에 없는 인과관계, 새로운 반박 사실의 창작을 거절함.
- 거절 이유에 출처가 있는 경우 **툴 이름·결과 인덱스·원문 위치**를 포함하도록 지시함.
- 검색 미발견을 근거 없는 직접 모순으로 간주하지 않음.

C는 A의 Alignment·Coverage·Action을 재심사하지 않음. B가 추출한 주장을 C가 빠뜨리거나 중복 판정하면 프로토콜 위반으로 실패하도록 검사함.

## 임시 답변 승인 및 재조회 루프

본체 모델이 툴 호출을 마친 뒤 생성하는 답변은 사용자에게 아직 공개하지 않은 **임시 답변 후보**임. 이 후보를 A/B/C Verifier가 검증함.

- **PASS:** 임시 답변의 본문을 그대로 사용자에게 출력하고 현재 AgentLoop 실행을 종료함. 검증 모델이 최종 답변을 별도로 작성하지 않음.
- **REJECTED:** 사용자에게 해당 임시 답변을 출력하지 않음. 거절한 주장·문제 유형·근거·수정 사유 및 최신 거절 초안을 본체 모델의 다음 라운드 입력으로 전달함.
- 본체 모델은 다음 라운드에서도 툴을 사용할 수 있음. 검증 범위에서 근거를 못 찾았다면 필요한 파일/웹 자료를 재조회하거나, 뒷받침되지 않는 주장을 제거하고 다시 임시 답변을 제출할 수 있음.
- **툴 실행 기록이 실제 성공 결과를 추가했다면** 이전 후보를 반복해서 거절한 횟수 예산을 새로 시작함. 새 근거 없이 반복되는 거절에는 기존 축별 재시도 예산이 적용됨.
- Verifier 예외나 구조화 출력 계약 위반은 자동 승인되지 않으며 실행 오류로 드러남.

## 최종 판정 및 재시도

`FinalGroundingVerifier.verify()`가 각 단계의 구조화된 판정을 `FinalVerificationResult`로 결합함. A에서 거절할 경우 A의 사유를 사용하고, C에서 거절할 경우 해당 주장과 사유를 본체 모델의 수정 피드백에 포함함.

기존 **별도 Numeric Reviewer**와 기존의 모든 툴 결과를 압축해 한 번에 판정하는 **일괄 Final Reviewer**는 호출하지 않음. 다만 AgentLoop의 축별 답변 수정 재시도 예산 및 인터페이스는 일부 유지함. 통합 검증 중 인프라/출력 계약 오류를 조용히 승인으로 바꾸지 않음.

## 구현상 제약과 점검

- A가 전체 툴 결과를 받으므로 컨텍스트 비용과 지연이 늘어날 수 있으며, Ollama 컨텍스트 한계를 넘어갈 수 있음.
- B가 적절한 원문 검색어를 만들지 못하면 C의 증거 범위가 좁아짐.
- 마지막 툴 실행 라운드만 선택하므로 오래된 핵심 자료를 제외할 수 있음. 필요한 경우 본체 모델이 툴을 다시 호출해 근거를 갱신해야 함.
- 검색·판정 프로토콜에 변경이 생기면 `tests/test_verifier_evidence_retrieval.py`, `tests/test_verifier_integrated_review.py`의 계약 테스트를 함께 수정해야 함.
- 실제 Ollama 환경의 정밀도·지연 및 긴 입력의 동작은 별도 통합 테스트가 필요함.
